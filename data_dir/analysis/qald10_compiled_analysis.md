**What goes wrong most of the time**

| # | Recurring failure mode | Why it happens (root cause) |
|---|------------------------|-----------------------------|
| **1. Entity‑linking misses or mis‑identifies the subject(s)** | • The NER/linker returns an empty list or a wrong Q‑ID (e.g. “Running Wild”, “Lisa Manoban”, “Cornetto trilogy”, “Sahara Desert”). <br>• No fallback to a label‑search is provided. | The pipeline never seeds the downstream steps with a concrete entity, so the LLM is forced to guess IDs or to work with generic triples. |
| **2. Relation‑extraction picks the wrong predicate or drops the needed one** | • “official language” → P37 instead of P2936, “award received” → P166 but the correct subclass hierarchy is ignored, “capital‑of” → P206 instead of the required P36 + P2046 chain, etc. <br>• Qualifier‑aware patterns (start‑/end‑time, language qualifiers, “member‑of” with P155/P156) are never extracted. | The extractor relies on surface‑form similarity only and has a limited predicate lexicon; it also discards low‑frequency but semantically crucial patterns. |
| **3. Hop‑expansion stops too early** | • The search never reaches a needed property (area, inception, birth‑place → country, temporal qualifier, P527 “has part”, etc.) and the system falls back to a generic pattern. | Fixed hop limits or a “stop‑when‑no‑new‑pattern” rule prevents the graph walk from discovering deeper edges. |
| **4. The LLM is allowed to hallucinate predicates / triples** | • Uses P571 when no inception triple was found, P2002 for Twitter when only P463 existed, P456 (…​) that never appeared in the candidate set. | The generation prompt does not enforce “use only supplied patterns” and there is no validator before the query is emitted. |
| **5. Missing type / filter constraints** | • No `wdt:P31 wd:Q6256` when counting countries, no `instance‑of film` when counting movies, no language‑class filter for verbs, no “state of Germany” type, etc. | The ranking step discards useful `P31/P279*` patterns; the LLM never adds a class filter unless it is explicitly present. |
| **6. Wrong query shape** | • Produces a `SELECT` where a boolean `ASK` is required, returns two variables instead of a single `?result`, omits required prefixes, uses `VALUES … ORDER BY` instead of `BIND(IF…)`, fails to use `DISTINCT`. | Prompt does not tell the model the expected answer format; post‑processing does not check variable names, prefixes or aggregation semantics. |
| **7. Temporal / qualifier handling is absent** | • Ignores `pq:P580`/`pq:P582` on “capital‑of”, does not filter by year when asked for “since 2010”, never uses `P580`/`P582` for “in 934”, etc. | The extractor never pulls qualifier triples; the generator treats qualifiers as ordinary properties. |
| **8. Inadequate pattern‑ranking / bias** | • High‑frequency but irrelevant predicates (P166, P451) outrank the needed one, the model prefers “official language” over “language used”, or selects “award‑received” only for a specific subclass. | Similarity scoring does not incorporate the question’s cue words (e.g. “bigger”, “compare”, “only”, “spoken”), nor any notion of answer‑type constraints. |
| **9. No validation of completeness** | • The system never checks whether the generated query contains all required predicates (e.g. P31 + P27 + P166) before returning it. | Missing a cheap “does‑the‑query cover‑all‑required‑triples” test leads to silent mismatches. |
| **10. Prefixes / syntax omissions** | • Queries miss the mandatory `PREFIX wd: …` block, use `SERVICE wikibase:label` when disallowed, or produce malformed `STRLEN` calls. | The generation module is not forced to output a syntactically‑complete SPARQL template. |

---

**How to fix them – a roadmap of concrete improvements**

| Failure mode | Suggested fixes (grouped by component) |
|--------------|----------------------------------------|
| **Entity‑linking** | • Upgrade the linker (e.g. combine a fast fuzzy‑match gazetteer with a Wikidata search API). <br>• Add a “fallback‑by‑label” step that, when no Q‑ID is found, issues a `wd:??` lookup before generation. <br>• Validate that each mention in the question yields a non‑empty Q‑ID; if not, request a second pass or raise a clear error. |
| **Relation extraction** | • Enrich the predicate lexicon with all Wikidata properties that appear in the training set (including qualifiers). <br>• Map high‑level verbs to the exact P‑property (e.g. “speak” → P2936, “was married to” → P26, “started” → P580). <br>• Keep *both* direction‑variants of a property (subject‑object vs object‑subject) and expose qualifier triples (`p:…/ps:…/pq:…`). |
| **Hop‑expansion** | • Replace a fixed hop limit with a **goal‑driven** stop condition: stop only when every property required by the question is present (area, inception, country, etc.). <br>• When a required predicate is missing, automatically issue a targeted lookup (`wd:Qxxx wdt:Pyyy ?v`) before giving up. |
| **Prevent hallucination** | • Mask the LLM’s output: give it a list of *allowed* predicates and require it to pick from that list. <br>• Add a post‑generation validator that rejects any predicate not seen in the candidate‑pattern set (or forces a second hop to retrieve it). |
| **Type / filter constraints** | • Always include `P31`/`P279*` patterns in the candidate pool; rank them high when the question mentions a class or expects a restriction. <br>• Insert a post‑processing rule that adds a missing `instance‑of` triple if the result set is not already filtered to the expected type. |
| **Query‑shape enforcement** | • Encode the expected answer form in the prompt (e.g. “Return a Boolean ASK query” for yes/no, “Return only ?result” for comparison). <br>• After generation, run a lightweight syntax/shape checker: correct variable name, required prefixes, presence of `DISTINCT` or `BIND(IF…)` as dictated by the gold template. |
| **Temporal & qualifier handling** | • When a time‑related cue word (“in 2000”, “since 2010”, “beginning”) appears, force the extractor to surface any `pq:P580`, `pq:P582`, `P585`, `P577` patterns. <br>• Provide a template for qualifier‑aware patterns (`p:P166/ps:P166 … pq:P580 …`). |
| **Ranking / bias correction** | • Augment the similarity score with a **signal from the question**: word‑level cues → target predicate, required arity, answer type (count vs list vs boolean). <br>• Use a small supervised reranker that learns to push gold‑property patterns to the top (e.g. via pairwise preference loss). |
| **Completeness validation** | • Before handing the pattern set to the LLM, compute the *coverage*: does the set contain at least one triple for every property the gold query uses? If not, trigger another expansion. |
| **Prefix & syntax hygiene** | • Wrap the generation module in a templated wrapper that always prepends the standard `PREFIX` block. <br>• Run the produced query through a SPARQL parser (e.g. `rdflib`) to catch missing parentheses, illegal `STRLEN` on language‑tagged literals, etc. |
| **General orchestration** | • **Iterative refinement**: generate a draft query → run a quick dry‑run against the endpoint → if missing bindings or unexpected result shape, request another expansion or a different predicate list. <br>• **Logging & fallback**: keep a trace of why a particular pattern was discarded (low score, missing qualifier, etc.) so that developers can tune thresholds. |

---

**Bottom line**

The majority of mismatches stem from *missing or wrong grounding* (entities or predicates) and from a *lack of enforcement* that the generated SPARQL must respect the grounding that does exist. Strengthening the upstream linker, making the relation‑extraction richer and goal‑driven, and tightly constraining the language model to use only the retrieved patterns (plus a simple validator for shape, prefixes, and required qualifiers) will eliminate most of the failure modes listed above. Once the grounding is reliable, a lightweight prompt change (explicitly state the desired query form) and a post‑generation sanity‑check are enough to bring the generated SPARQL into alignment with the gold answers.
